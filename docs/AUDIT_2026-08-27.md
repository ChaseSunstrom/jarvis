## 4. The server's capabilities, the console, the agentic loop

**Server** (`audit-server.md`): 86 tools live, every websocket command in `clients.md` answers;
ten defects. The serious one: `read_page` (Tier 1, read-only, callable on a tainted turn) read
`http://127.0.0.1:8080/healthz` from inside the core while `web_fetch` for the same URL was
refused — the watch integration's plain-`httpx` fallback ran on *any* browser error with no
address check. Then: an empty `automations.yaml`/`scenes.yaml` produced a phantom
`automation.automation_0` and `scene.scene_0` (on, exposed) on every house; `n8n:` appeared twice
in `configuration.yaml` (PyYAML kept the last, silently); three Settings rows said the wrong thing
(`llm.fast_model` "read by nothing yet", `demo.enabled` `null` for a fixture house that was up,
`voice.speaker.mode` `false` against `[off, observe, enforce]`); `POST /api/sensor/<id>` documented
and absent; REST undocumented; a failed coding job's steps never say so (M82).

**Console** (`audit-console.md`): every command the console sends exists on the server and in the
mock, and the four states are real on every screen — but two unwraps were wrong in the same way:
`pendingApprovals()` read `response` as the list (the server sends `{response: {pending}}`), so
the approvals banner never seeded from a real server; `N8nConnection` read `service_response`
(Home Assistant's REST name) and showed "connected" to a house with no n8n. Neither test caught
it because the mock encoded the console's assumption. Areas and ScheduledJobs are not live
(no subscriptions); there is no RETRY though `jarvis/tasks/retry` exists; several server fields
are sent and never shown.

**Agentic** (`audit-agentic.md`): memory, notes, schedules, automations by voice, background
tasks, research, coding, subagents, skills, self-authored tools, the surface, undo and the
speaker line all exist; the briefing and the narrator (noticing) were built and never enabled;
"Make a note that the audit ran" was answered "Done, Sir — noted." with nothing called and no
note written — the claimed-action guard had no record verbs; `get_user_context` read the
process clock, not the house's; finished work writes an inbox card and never speaks; Jarvis
cannot read its own inbox or trace; memory does not consolidate (two entries for one name) and is
not per-person; the room a request came from is dropped at the `converse` boundary; there is no
server-side stop. Twelve features proposed, folded into M84–M97 below.

**Phone** (`audit-android.md`): the mirrors pin the Kotlin they name and the shared contract tables
are read by both suites; four defects. A new phone against an *enforcing* house refuses every turn
— `speakerGateEnforcing` defaults false, is written only after the Whose-voice screen, and Settings
says "speech is turned into text on this phone" in the calm colour while the server refuses the
audio-derived turns; the Tasker engine (`TaskStore`) has no way in — nothing on the server ships a
task definition, and PHONE TASKS tells the user tasks "arrive from jarvis-core"; a held Tier-3
action cannot be approved from the phone (a strip row with no affordance — the one surface with a
keyguard-aware consent screen); and the tier contract's phone mirror pins a property the Kotlin
does not have (the phone asks on tier 2 too, once). Parity: the console's type-to-Jarvis, the
held-request bar, the surface panels and the task dock have no phone counterpart.

## 6. The plan — M84 onwards (draft, refined by §4)

What would make Jarvis feel less like a voice remote and more like a butler who *runs the
house*: it volunteers, it remembers across days, it finishes what it started, it can be asked
why, and every one of those is verified on the live house the way the operator uses it.

| # | milestone | the user experiences | builds on |
|---|---|---|---|
| M84 | **Jarvis volunteers a briefing** | at 07:00 and 22:00 Jarvis says what the day holds — weather, calendar, what needs attention, what quietly stopped working — and "what's my briefing?" answers any time | `integrations/briefing` exists, is not enabled on the house, and `get_briefing` is not registered |
| M85 | **Work survives a restart** | a background job interrupted by a restart resumes from its last step instead of dying "interrupted when Jarvis restarted" (four such tasks on the house tonight) | the task engine persists steps (`load_persisted` in the orchestrator; the core's task store) |
| M86 | **Jarvis notices** | a door left unlocked after midnight, a sensor stuck for hours, a device that went offline: one spoken nudge with a one-tap action, never a stream | `watch_for`, notifications, presence (`companion.notify`), `undo` |
| M87 | **Overnight reflection** | each night the day's conversations are consolidated into a handful of durable facts and a "what I learned" card the user can review, edit or discard | memory store + recall, notes, the archive (`llm/history.py`) |
| M88 | **A plan on the screen** | a multi-step job shows its plan on the voice screen as a panel — steps ticking, the current one live, a "stop" — and Jarvis narrates checkpoints only | the surface (M83), tasks' step events (M10) |
| M89 | **Stack hygiene** | SearXNG on loopback, `jarvis-web` not root, the live sandbox pinned by a test, the isolation matrix true | services audit §1 |
| M90 | **The claims register, re-measured** | `docs/verification.md` says one number per suite, dated, with the command beside it; the four pessimistic rows corrected; no row names a component that no longer exists | quality audit §1 |
| M91 | **A gate cannot pass on a skip** | `lib.sh`'s pytest checks fail on `skipped`/`no tests ran`; each live slice writes its own results file so a red smoke names its scenario | quality audit §2 |
| M92 | **The house by voice, beyond lights** | climate, covers, scenes, scripts, media, `note_append`, `sensor_compare`, the moon, a feed watch, a spoken question answered by the next turn, `show` by voice — each a live scenario | quality audit §3 |
| M93 | **Pick up where you left off** | the console has a URL per conversation; the phone opens the same thread; the rig drives multi-turn console scenarios in `--full` | FUTURE #1, #4 |
