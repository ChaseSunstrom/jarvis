## 2. Seams (ranked)

1. **The briefing and the narrator are documented as running and are not on.** `docs/features.md:22` ("Reads the live house twice a day"), `docs/verification.md` and M17's scope all describe the briefing; `config/configuration.yaml` has no `briefing:` and no `narrate:` key, so neither integration loads (`core.py:205` sets up only configured integrations). Live: `not_configured`, no `get_briefing`/`recent_events` tool, zero briefing moments, and the model fakes a briefing from the prompt when asked. Two config blocks and a Settings row fix it.
2. **"Make a note" was claimed and not done, and the guard let it through.** `_ACTION_REQUEST` (`agent.py:2285`) lists turn/switch/set/lock/… but no note/remember/schedule/remind/watch verbs, so `claimed_action` (`:2390`) never looked at "Done, Sir — noted." `TOOL_RULES` says "make a note" is `note_create`; the live house has 0 notes after being told "Done". The `notes-write-and-find` scenario passes on a fresh conversation; on a conversation with history it did not call the tool. Extend the regex (note|remember|remind|schedule|watch|forget) and the constrained retry already does the rest.
3. **The routing policy is blind and reads the wrong clock.** `get_user_context` (`tools.py:2301`) — the one thing `DEFAULT_PERSONA` rule 3 tells the model to call — returned `home: null, presence_state: null, awake: false, hour: 4` at 22:50 local: no `person.*` entity on the house, and `time.localtime()` is UTC in the container while `clock_line` uses `configured_clock`. `PresenceRegistry` (connected devices, `companion/presence.py`) knows more and the model never sees it.
4. **Finished work does not speak.** `jarvis_task_completed` → inbox record only (`notifications/__init__.py:268-301`); only `schedule`'s `notify`, the briefing and `narrate` call `companion.notify`. "Tell me when it is done" is a card, not a voice; the `interactions-proactive-moment` scenario asserts the record and nothing more. The tier contract says Tier 2 is `announced: true` (`/tests/contracts/tool_tiers.json`) and nothing announces.
5. **Jarvis cannot read its own inbox or trace.** No tool over `notifications` (14 moments) or `observability` (`/api/traces`); `memory_used` is not in the trace. "What did you tell me earlier?" and "Why did you do that?" are answered by reconstruction — live, it apologised for a mistake it had not made.
6. **The task engine's restart and cancel promises do not hold.** `docs/tasks.md` says queued work survives a restart; `TaskEngine.register_kind` (`taskengine.py:165`) has no caller, so every restored item fails "no worker for 'background'". Cancelling a *queued* task is overwritten when `_drive` marks it running (`taskengine.py:314`; `tasks.py:523` has no terminal guard). Research (`research/__init__.py:438`) and code (`code/__init__.py:1004`) still `ensure_future` past the concurrency cap the engine exists to enforce.
7. **Memory does not consolidate and is not per-person.** Extraction wrote "The speaker's name is Chase" beside "The user's name is Chase"; `_duplicate_of` (`memory:612`) is exact-ish text. M71 names the speaker in the prompt; memory has no speaker field, so a two-person house shares one set of "the user" facts.
8. **The room is dropped at the `converse` boundary.** `device_id` reaches the pipeline run (`pipeline.py:326`) and the speaker verdict, not the model (`:1249-1295`). `tell_user` ("whichever device they are actually at") cannot prefer the room that asked.
9. **`create_tool`: one approval, then Tier 1 forever.** `build_yaml_tool` reads `tier` from the model's own manifest, default 1 (`tools.py:3848`); nothing tells the user a tool was added, on the Tools screen or by voice.
10. **Two presences, two clocks, two traces, two `n8n:` keys.** Beyond 3 and 5: `config/configuration.yaml` has `n8n:` at lines 702 and 1579 (PyYAML keeps the last, silently). `orchestrator` (5 tools) and `web` (4) register when unconfigured; `n8n` documents why it must not (`n8n/__init__.py:445`).
11. **No server-side stop.** Barge-in is a client dropping the socket; a run has no `stop` command, and a trace cannot say "interrupted".
12. **Scenario gaps** (`testing/live/scenarios/`, 47 files): nothing exercises the briefing, undo, `create_automation`, `create_tool`, `show` by voice, a recurring schedule, `get_user_context` routing, a two-client thread, narrate/noticing, the speaker line, calendar/mail, channel *outbound*. Only two scenarios name a `tool:` expectation at all (`start_coding_job`); the rest assert on `reply_means`, which cannot catch Seam 2.
13. **Stale prose.** `docs/architecture.md` still draws "Ollama qwen3:8b"; the house runs `qwen3.8-27b` behind LiteLLM (BLOCKERS §2). `docs/AUDIT.md` §13–§15 are the pre-milestone baseline (memory UI "missing", notes "missing") and read as current.

## 3. Proposed features (ranked by user value ÷ effort)

**F1 — Switch the briefing on, and let Jarvis read it (S, high).** The user hears a short digest at 07:00 and 22:00 on whichever device they are at, and "give me my briefing" by voice reads the same thing rather than an improvisation. Exists: the whole `integrations/briefing/` (sections, caps, `companion.notify`, `get_briefing`, `briefing_ready` → inbox). New: a `briefing:` block in `config/configuration.yaml` pinned by `test_packaging.py`, a Settings › Assistant row for the two slots, an `overnight` section built from the inbox and the logbook since the last briefing ("two reminders fired, one research run failed"), and `mark_untrusted_result` on calendar/todo text as `features.md:65` already asks. Scenario:
```yaml
name: briefing-on-demand
turns:
  - say: "Give me my briefing."
    expect: {tool: get_briefing, reply_means: "reads what is unlocked, open or unavailable and what fired overnight; does not invent a calendar"}
  - observe: true          # the rig sets briefing.evening one minute ahead through settings first
    wait: 90
    expect: {notification: {kind: briefing, within: 30}}
```
Risk: Tier 1, read-only; the calendar section must taint the turn once a calendar exists.

**F2 — Finished work speaks, and the policy that routes it can see (S, high).** "Look into X and tell me later" ends with Jarvis saying so in the room you are in (or a phone card if you are out), not a silent inbox row. Exists: `companion.notify` + `presence.route` (`companion/presence.py:195`), the `task` trigger platform (`docs/hooks.md:55`), the inbox record. New: a listener on `jarvis_task_completed/failed` that calls `companion.notify` with the task's spoken summary; `get_user_context` reads `configured_clock` and falls back to `PresenceRegistry` reach levels when no `person.*` exists; the reply's `guidance` becomes data (`home`, `reach`, `active_device`) the model can act on. Scenario: extend `interactions-proactive-moment` with `expect: {companion: {kind: say, within: 240}}` on the `text-ui` variant, and a new `routing-context` turn: say "Where am I, as far as you can tell?" → `tool: get_user_context`, reply names the device the rig is connected from. Risk: Tier 1; respect quiet hours and `driving`.

**F3 — An inbox and a trace Jarvis can read: `recent_moments` and `explain_last_turn` (S, high).** "What did you tell me while I was out?" lists the moments; "why did you say that?" names the tools and the remembered notes the previous turn actually used, from the record, never reconstructed. Exists: the notifications record, `ConversationArchive` with tool calls per turn (`llm/history.py`), `observability` spans, `memory_used`. New: two Tier-1 read-only tools; `memory_used` and the prompt's note ids written into the observability trace; a `TOOL_RULES` line "asked why, read the trace — never reconstruct". Scenario:
```yaml
name: explain-yourself
turns:
  - say: "What's the temperature in the garage?"
    expect: {tool: sensor_readings}
  - say: "Why did you say that? What did you look at?"
    expect: {tool: explain_last_turn, reply_means: "names the sensor tool it used last turn and makes no new sensor call"}
```
Risk: none beyond prompt budget; results are server-authored, not untrusted.

**F4 — Noticing: rules that ship, with one-tap actions (M, high).** At night an unlocked door, a window left open, a sensor that has gone quiet or a device that went unavailable produces a spoken nudge ("the back door has been unlocked since 23:10, Sir — shall I lock it?") and a moment card with the action on it. Exists: `narrate` (rules, debounce, quiet hours, critical classes), `expire_after` → unavailable, `companion.ask` (M66 makes the yes sayable), the `moments` surface panel, the briefing's unlocked/open/unavailable detectors. New: a `narrate:` block on by default with four rules (lock unlocked after quiet-hours start, opening open > 30 min at night, `unavailable` > 10 min, no change over 2× expire window = "stuck"); a `notice` moment kind carrying `actions: [{tool, arguments}]`, drawn as buttons on console/phone; the nudge asked through `companion.ask` so the answer routes to the held `lock_control`. Scenario:
```yaml
name: notice-unlocked-at-night
turns:
  - observe: true          # the rig unlocks the fixture lock through the API with quiet hours set to "now"
    wait: 60
    expect: {notification: {kind: notice, title_contains: unlocked, within: 60}}
  - say: "Yes, lock it."
    expect: {approval: {tool: lock_control, decision: approve}, state: {lock.front_door: locked}}
```
Risk: the notice is read-only; every action stays behind its own tier (`lock` is a gated domain). Debounce and the four global ceilings already exist.

**F5 — Nightly reflection: "what I learned today", reviewable (M, high).** Each night Jarvis folds the day's extracted facts and conversations into a few durable, deduplicated memories and one note the user can read on the Memory screen — each proposal a tap to keep or forget, none applied as an instruction. Exists: `async_extract`, the archive, `_duplicate_of`, pinning, the Memory UI, the `once/daily` scheduler, `ask_once` (a no-persona model call). New: a `memory.reflect` service run daily (default 03:00 house time) that reads the day's archive + `source: extracted` entries, merges near-duplicates by embedding similarity (the vector sidecar already exists), writes proposals with `source: reflection, pending: true`, and a `note` "What I learned on <date>"; the prompt block excludes pending proposals; a `reflection` moment links to the review. Scenario:
```yaml
name: memory-reflection
turns:
  - say: "My daughter is called Mira and she is allergic to peanuts."
  - say: "Remember that Mira, my daughter, can't have peanuts."
  - observe: true          # the rig calls memory.reflect through the service API
    expect: {memory: {count_matching: {query: "Mira peanuts", equals: 1}}, notification: {kind: reflection, within: 120}}
```
Risk: writes into every future prompt — proposals are pending until tapped; tainted turns are excluded (`turn_is_untrusted`); never writes on a channel conversation.

**F6 — Room-aware requests (S, medium-high).** "Turn off the lights in here", "show the camera on this screen", "remind me here in ten minutes" resolve to the room and device the request came from. Exists: `PipelineRun.device_id`, the device registry's area, `speaker_line`'s pattern for a last prompt line, `show`'s surface, `tell_user`. New: `converse(..., device_id=, area=)` from `_call_converse`; one prompt line after the speaker line ("You were spoken to from the Kitchen, on the wall panel"); `remember_turn` stamps the device so `tell_user`/`show`/`schedule_task` default to it. Scenario: `room-aware` — the rig registers its client device in `Kitchen`; say "Turn on the lights in here" → `expect: {service: light.turn_on, entity_id: light.kitchen_lights}`; say "Put the front door camera up on this screen" → `expect: {tool: show}` and `jarvis/surface/list` names the panel. Risk: context only, never authority — the tiers are unchanged.

**F7 — Routines by voice, said back and listed (S, medium).** "Every weekday at seven turn on the kitchen lights and start the coffee" becomes an automation, and Jarvis reads the schedule back ("weekdays at 07:00: kitchen lights on, coffee machine on") and can list and describe routines later. Exists: `create_automation` with its gate, `automation.check` dry-run, `AuthoredStore`, the Automations screen, the `time`/`sun`/`state` triggers. New: `automation.check` run before every creation with the plain-English read-back in the reply; a `list_automations`/`describe_automation` Tier-1 tool (there is none — `automation_control` acts, it does not describe); the Tier-2 "announced" semantics honoured by an `automation` moment. Scenario:
```yaml
name: routine-by-voice
turns:
  - say: "Every weekday at seven in the morning, turn on the kitchen lights."
    expect: {tool: create_automation, automation: {alias_contains: kitchen, trigger: time, within: 30}, reply_means: "reads back weekdays at 07:00 and the kitchen lights"}
  - say: "What routines do I have?"
    expect: {tool: list_automations, reply_means: "names the weekday kitchen-lights routine"}
```
Risk: Tier 1 unless an action reaches a gated domain (already escalates); the read-back is what lets a person catch a wrong trigger.

**F8 — Goal-directed tasks with the plan on the surface, and checkpoints that ask (M, high).** A background job shows its plan beside the instrument as it runs — steps, the current one, what each produced — and a step that needs approval pauses the job and asks instead of failing it. Exists: `plan_and_run` writes steps to the task, `jarvis_task_*` events, the surface's panel model, `companion.ask` + M66, `raise_if_cancelled`. New: a `task` panel kind auto-placed on the originating device when `run_background_task` starts (removed on completion or on "clear the screen"); a checkpoint in `run_plan` — an `approval_required` outcome parks the plan, raises the request on the task's conversation, resumes on the answer; `needs_a_plan()` offered to interactive turns when the think tool fires. Scenario: `task-plan-visible` — say "In the background, check every light downstairs, then make a note listing which are on, and tell me when it is done" → `expect: {task: {kind: background, steps_min: 2, within: 45}, surface: {kind: task, within: 15}, note: {title_contains: lights, within: 240}, notification: {kind: task, within: 240}}`. Risk: a checkpoint holds Tier-3 steps exactly as a turn does; the 240 s budget is BLOCKERS §2's problem, not this feature's.

**F9 — Continuity as a link and a handoff (S, medium).** "Carry on with this on my phone" moves the thread; a conversation has a URL the console, the phone and the rig can open. Exists: server-side threads by id, `companion.handoff` = `say(conversation_id)`, Android's `ConversationRegistry`, `testing/e2e/test_continuity.py`. New: `?conversation=<id>` on the voice screen (`docs/FUTURE.md` #4) with the id shown on the page; a `handoff` Tier-1 tool wrapping `companion.handoff` to the named or most-recent other device; a two-client live scenario. Scenario: `continuity-two-clients` — turn 1 through the API "Turn on the bed light" on `conversation_id: rig-cont`; turn 2 through the console (`text-ui`) opened at `?conversation=rig-cont` "What did I just ask you?" → `reply_means: "the bed light"`. Risk: none; a handoff carries text and a question, never an authorisation (`docs/cross-device.md:146`).

**F10 — Interruptible turns (S, medium).** Saying "Jarvis, stop" (or tapping) stops speech and the model *at the server*, and the trace says "interrupted". Exists: `aclosing` on the round generator, `OllamaStream.aclose`, client-side barge-in on both surfaces, the observability trace. New: an `assist_pipeline/stop {run_id}` websocket command and REST twin that cancels the run's task (closing the stream and dropping queued `tts-chunk`s), an `interrupted` reason on `run-end`, an `interrupted` span. Scenario: `voice-barge-in` — say a research question on the voice variant; on the first `tts-chunk` the rig sends `stop`; `expect: {run_end: {reason: interrupted, within: 5}, no_further: tts-chunk}`.
