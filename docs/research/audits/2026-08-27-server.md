## Defects, ranked

### 1. `read_page` bypasses the private-address block — a Tier-1 tool reads loopback and LAN HTTP (broken, security)

`jarvis/integrations/watch/__init__.py:380–402`: `fetch_text` asks `web.fetch` (jarvis-browser) first; on *any* error — the comment names "a refused host" — it logs at INFO and fetches the URL itself with `httpx` (`follow_redirects=True`, no address check). `fetch_feed` (`feed_latest`, `watch_feed`) and `watch_page` never go through the browser at all. jarvis-browser's `is_blocked_host` (`jarvis-browser/jarvis_browser/safety.py`, promised in `docs/search.md:205–209`) therefore guards `web_fetch`/`web_crawl`/`web_browse` and nothing else.

Reproduction (live):

```
ws.py jarvis/tools/call '{"name":"web_fetch","arguments":{"url":"http://127.0.0.1:8080/healthz"}}'
  → status error: "jarvis-browser returned HTTP 403 on /fetch: refused: host '127.0.0.1' resolves to a blocked (private/local) address"
ws.py jarvis/tools/call '{"name":"read_page","arguments":{"url":"http://127.0.0.1:8080/healthz"}}'
  → text: <untrusted_web_content>… {"status":"ok","version":"0.1.0","running":true,"entities":31} …, chars: 62
```

Reach: `read_page` is Tier 1 and on `READ_ONLY_TOOLS`, so a tainted turn may still call it. From the core container (host networking) it reaches the orchestrator (`:8188`), the gateway, SearXNG, Radicale, the mailsink, and jarvis-core's own open routes — a `GET /api/webhook/<id>` through `read_page` fires that webhook. `docs/verification.md:1109` records the opposite property as Automated; `test_watch.py:260` asserts it only when the browser succeeds. The fallback arrived in `66a7b43` under a subject about tool rounds.

### 2. Empty `automations.yaml` / `scenes.yaml` produce a phantom automation and scene (broken)

`jarvis/config.py:207` `return yaml.load(handle, Loader=_Loader) or {}` turns an included `[]` into `{}`; `jarvis/automation/util.py:139` `as_list({})` → `[{}]`; the automation and scene integrations build one entity from the empty dict.

Reproduction: `curl -H "Authorization: Bearer $T" :8080/api/states/automation.automation_0` → `state: on`, `attributes.id: automation_0`; `ws.py config/automation/list` → one row, `trigger: [], action: [], editable: false`; `scene.scene_0` likewise. Both are `exposed: true` in the registry, so the model's `list_entities` and the console's Automations page show an automation nobody wrote and cannot delete.

### 3. `POST /api/sensor/<id>` is the documented way in and does not exist (misleading docs)

`jarvis-core/docs/sensors.md:38–80` gives it as "Way 2" with four curl examples and a response body. `jarvis/api/rest.py` has no such route; `GET /api/openapi.json` lacks it; live `GET`/`OPTIONS /api/sensor/audit_probe` → 404 (`{"detail":"Not Found"}`; a mounted POST-only route answers 405). The integration publishes the handler at `jarvis.data["sensor_ingest"]` with `path = "/api/sensor/{sensor_id}"` for "the API layer to mount … until it does" (`sensors/__init__.py:52–60`); nothing under `jarvis/api/` references `sensor_ingest`. Only `POST /api/webhook/sensor?sensor_id=` works.

### 4. `n8n:` twice in `configuration.yaml`; the loader keeps the last silently (config, misleading comment, missing docs)

`configuration.yaml:702` (M37: `enabled: false`, `url`, `workflows: []`) and `:1579` (M77: `url`, `api_key`, `assistant_url`, `timeout`). `jarvis/config.py` has no duplicate-key detection, so the first block is dead. Its comment block (`:695–701`) describes tier and webhook semantics the M77 integration does not have, and `:1574` says "Empty url means off — the tools then say so", while `n8n/__init__.py:443–449` registers no tools when unconfigured (log: "n8n: not configured … no tools registered"). n8n has no section in `docs/integrations.md` or `docs/configuration.md`.

### 5. Three settings rows say the wrong thing (misleading; the operator reads Settings)

- `llm.fast_model` note: "Recorded on the running agent, and read by nothing yet: the fast path lands with M60" — `integrations/voice/__init__.py:271–291` routes spoken turns to it; M60 is ticked.
- `demo.enabled`: `value: null` (`source: package`) while `demo/__init__.py:539` defaults `enabled` to `True` and the fixture house is up (lights, lock, garage, vacuum all present). A boolean with no value cannot be drawn as on.

Reproduction: `ws.py config/settings/list` → the three rows above.

## Suggested milestones

1. **One fetch guard** — a shared `is_blocked_host` in jarvis-core applied to `read_page`, `watch_page`, `feed_latest`, `watch_feed` and every model-steerable `httpx` fetch, with the browser's refusal final rather than a fallback; a test that a 403 from jarvis-browser never turns into a plain fetch; re-measure `verification.md:1109`. Closes Defect 1.
2. **Empty includes stay empty** — `load_yaml` keeps a list document as `[]`; `test_packaging` pins that the default house boots with no `automation.*`/`scene.*` entities. Closes Defect 2.
3. **The sensor door** — mount `POST/PUT /api/sensor/{sensor_id}` from `jarvis.data["sensor_ingest"]` (the handler already answers `ok`/`status`), or rewrite `sensors.md` "Way 2" to the webhook door; pin the doc's routes against `/api/openapi.json`. Closes Defect 3.
4. **One n8n block** — delete the M37 block and its comments, make `jarvis/config.py` refuse a duplicate top-level key with the line numbers, add an n8n section to `integrations.md`. Closes Defect 4.
5. **Settings tell the truth** — fix the `fast_model` note, give `demo.enabled` its real default, normalise YAML booleans for choice settings; a test that every choice setting's live `value` is one of its `choices`; retire the `'demo mode'` example in `clients.md`. Closes Defects 5 and 6.
