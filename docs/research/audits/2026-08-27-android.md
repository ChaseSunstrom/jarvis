## Defects (ranked)

1. **A new phone against an enforcing house refuses every turn, and Settings says the opposite.**
   `KT/config/JarvisConfig.kt:207` defaults `speakerGateEnforcing=false`; `KT/config/JarvisConfig.kt`
   `sttOnDevice` defaults true; the only writer is `KT/VoiceIdentityActivity.kt:788` (after a
   `GET /api/voice/speaker`). `KT/assist/JarvisConversation.kt:398` therefore takes the local path,
   sends `audio_derived: true` (`KT/assist/AssistPipelineClient.kt:625`), and
   `jarvis-core/jarvis/voice/pipeline.py:694-715` refuses it. The KDoc at
   `JarvisConfig.kt:187-189` claims "the settings screen when it opens" refreshes it — `SettingsActivity`
   never queries the server (no `VoiceIdentityClient` in the file), so `strings.xml:200`
   ("Speech is turned into text on this phone. The recording never leaves it") is shown in the calm
   colour while every turn is being refused. The reverse (enforce→observe on the console) leaves the phone
   streaming with SUSPENDED on the line. No server push exists (`jarvis_setting_changed` is not consumed
   by the phone). Fix shape: read `mode` on every socket connect / `jarvis_setting_changed`, or have the
   server put `speaker_mode` in the register reply.

2. **The Tasker engine has no way in.** `TaskStore.upsert` / `import` / `replaceAll`
   (`KT/automation/tasks/TaskStore.kt:167,231`) have no caller in `src/main` outside the store;
   `AutomationsActivity.kt:36` admits it and `:270-272` still tells the user "Tasks arrive from
   jarvis-core over the device channel". The server's `run_device_sequence`
   (`jarvis-core/jarvis/integrations/device_control/__init__.py:883-900`) runs steps as individual
   `device_command`s and never ships a task definition; `ChannelFrames.kt` has no task frame. So the
   seven "Tasker itself" rows in `docs/ANDROID_TASKER_PARITY.md:218-226` (profiles, conditions,
   variables, sequences, loops, ask-mid-task, policy) describe code a user cannot reach, and
   `no_empty_seams_test.py` (the spec written for exactly this class of bug) does not cover `TaskStore`.

3. **A held Tier-3 action cannot be approved from the phone.** Deliberate on the server
   (`jarvis-core/jarvis/integrations/llm/__init__.py:606-609`: "a tier-3 ACTION deliberately stays on
   the surfaces that already show it"), but the phone is the one surface with a keyguard-aware,
   tapjacking-proof consent screen (`KT/ApprovalActivity.kt`, `KT/ui/ConsentGate.kt`), and the console's
   bar is a browser button. On the phone the request is a strip row "waiting for you"
   (`KT/assist/ActivityRows.kt:158`) with no affordance and no `summary` (`verification.md:746` "Not
   done"). Someone who says "unlock the door" to the phone and walks off has nothing to answer.

4. **The tier contract's phone mirror pins a property the Kotlin does not have.**
   `android-app/tools/tool_tiers_test.py:62-70` (`test_only_the_third_tier_asks`) asserts "the phone
   prompts only on 3" by checking that `CONFIRM -> Decision.ASK` exists; `KT/automation/policy/PolicyEngine.kt:56-57`
   also returns `ASK` for `NOTIFY` unless `ALLOW_ALWAYS` was stored — the README's "ask once, then
   remember" (`android-app/README.md:189`). `tests/contracts/tool_tiers.json:22-27` defines tier 2 as
   "Runs immediately … NOT an approval". Either the contract should record the phone's tier-2 variant
   or the phone should stop prompting; today `verification.md:333` says the three surfaces agree.
   The same contract's `$comment` (`:13`) and `rules.a_server_may_only_raise` (`:38`) name
   `policy_truth_table_test.py` and `jarvis-desktop/tests/test_policy.py` as readers; neither opens
   the file (only `tool_tiers_test.py` does).

5. **UI automation is presented as a feature the user can switch on.** Every shipped build has
   `PHONE_AUTOMATION=false` (`android-app/app/build.gradle.kts:77-81`); the accessibility service calls
   `disableSelf()` on connect (`KT/automation/accessibility/JarvisAccessibilityService.kt:75-78`) and
   `AutomationBridge.kt:348` refuses `ui_*` first. Yet `strings.xml:14-18` (the text Android shows in
   Settings › Accessibility) promises "Lets Jarvis read the screen and perform taps",
   `android-app/README.md:145-148`, `android-app/docs/ui-automation.md` (whole), `docs/actions.md` §delegated,
   `docs/automations.md` §Notifications, and `docs/ANDROID_TASKER_PARITY.md:139-147,127,131-132` (nine
   `ui_*` rows, `screen_on/off`, lock screen, screenshot marked **done**) say it works. The M61 gate
   (`scripts/verify/m61-android-tasker.sh:36`) accepts any `"ui_*"` string literal anywhere in the
   tree as "exists in the registry", so the flag never fails it.

6. **ActionPolicy screen mis-describes Tier 2.** `KT/automation/ui/ActionPolicyActivity.kt:600-602,758`
   ("Jarvis just does the harmless things, tells you about the middling ones" / "Tier 2 · runs and
   tells you afterwards") — with the default ASK a Tier-2 action shows the consent prompt
   (`PolicyEngine.kt:56-57`, `KT/automation/actions/ActionRegistry.kt:375`); no "tell you afterwards"
   notification path exists.
